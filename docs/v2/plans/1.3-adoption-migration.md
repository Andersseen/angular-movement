# 1.3 — Adoption & Migration

**Status: future plan; no implementation started.** Depends on shipped 1.2 contracts. This is the
single next recommended implementation milestone; no core API redesign or experimental promotion.

## Objective

Make adoption in existing Angular apps easier through correct tool selection, safe migration
assessment and reproducible package/runtime evidence.

## User story

As an Angular maintainer replacing legacy triggers, I can see what converts safely, which cases
should remain CSS/native Angular, and where coordinated Movement state/presence adds value.

## Current evidence

[014](../../ai/specs/014-consumer-dx-imperative-motion.md) found eight static consumers favoring
hover/tap/in-view/stagger/enter, timing/import mistakes, and pre-hydration CSS hero motion. No migration
tool exists; tarball consumer validation only installs/AOT-builds. [AUDIT](../AUDIT.md) identifies stale
variants/easing docs and missing packed SSR/hydration proof. Angular's official migration guidance
now offers native CSS/enter/leave, which must be included in comparison recipes.

## Scope

Conservative legacy assessment prototype, simple literal enter conversion only after eligibility
proof, reviewed leave/state/stagger recipes, Angular-native standalone imports, @if/@for identity,
reduced motion, SSR/first paint and route recipes using today's native Router. Correct confirmed docs
drift. Establish pinned packed browser/SSR/hydration baseline and consumer cohort.

## Non-goals

Universal conversion, arbitrary query timelines, automatic business callback removal, support for
legacy Angular runtime, core redesign, sequence API, Router provider or implementing later minors.
No speculative 2.0 rewrites and no command advertised before its package exists.

## Architecture implications

Migration needs TS/template semantic analysis and removal-owner detection. Keep compiler/CLI dependencies
outside core; choose schematic/optional development package only after report UX is proven. Leave may
need structural presence or native callbacks; an attribute alone cannot intercept @if destruction.

## Workstreams

1. Build fixture taxonomy and no-write confidence report, unsupported reasons and deterministic diffs.
2. Add reviewed recipes and direct CSS/native comparisons; fix docs identified by audit.
3. Add tarball runtime/server/hydration harness and supported-major minimum/latest policy.
4. Migrate two real apps with review, one SSR; log manual effort and unknown patterns.

## Likely code areas

Future tooling directory/package (name undecided), `validation/consumer/`, `scripts/validate-consumer.mjs`,
README/MIGRATION/site patterns, MCP guidance/tests and CI. Library changes require a separate narrower
spec; routine documentation work should not change barrel/API snapshot.

## Test strategy

Golden classifier/diff tests with aliased/dynamic/negative cases; untouched manual source stays
byte-identical; second run makes no changes. Compile converted templates from tarball, then execute
enter/leave/cancel/reduced-motion behavior. Hydrate actual server HTML; readiness checks cannot pass
without client handlers. Test no-JS and slow hydration. Use [VALIDATION](../VALIDATION.md) evidence record.

## Docs strategy

Publish “choose a primitive”, native/CSS comparisons, migration limits and before/after examples,
manual lifetime/track-key steps, install/import and first-paint guidance; version MCP advice with API.

## Migration impact

Opt-in assessment defaults to dry-run. Automatic eligibility is narrow; partial/manual findings are
successfully classified work. Preserve unsupported code/providers until no usages remain. Existing
Movement 1.2 users need no runtime change.

## Performance considerations

Record core/narrow-import and representative client frame baseline for later minors. CLI AST cost
is development-only; migration must not enlarge runtime merely to expose a command.

## Accessibility

Do not hide SSR content waiting for JS. Preserve links/focus/keyboard, functional leave state and OS
reduced-motion behavior. Warn when a conversion loses an accessible semantic, not just visual parity.

## Risks

False-confidence rewrites, dynamic legacy semantics, lifetime changes, comparison docs overselling
Movement, unsupported app Angular versions. Report unknown cases; require review before apply.

## Acceptance criteria

- [ ] Classifier emits automatic/partial/manual with file spans and concrete reasons.
- [ ] Every supported rewrite passes semantic fixtures, compile/runtime, dry-run/idempotence checks.
- [ ] Unsupported constructs remain intact; providers removed only with resolved no-use evidence.
- [ ] Native/CSS, @if/@for, SSR and reduced-motion recipes reviewed and confirmed drift corrected.
- [ ] Packed runtime/SSR/hydration baseline runs on supported majors; actual versions recorded.
- [ ] Two distinct migration apps reviewed, at least one SSR, with manual effort/bugs documented.

## Evidence required

Fixture reports/diffs, pinned tarball/app revisions, real browser/server logs, no-JS screenshots,
migration review and measured baseline. Static grep or two-major AOT alone does not meet the consumer gate.

## Maintainer decisions

Select projects and tool delivery; ratify minimum/latest Angular/device baseline; decide the literal
enter subset and whether any rewrite is mature enough to release versus diagnostics/recipes only.
A diagnostic-first release is acceptable if its adoption outcome is proved.
