# 1.7 — Gestures & Interaction

**Status: future plan; no implementation started.** Depends on 1.6 bounded layout and 1.4 ownership.
Gesture breadth is earned by application demand; bounded drag maturity is the required outcome.

## Objective

Make drag predictable under real touch, cancellation, constraints and layout interaction.

## User story

As an interactive app developer, I can drag a card on a phone, keep normal axis scrolling, cancel it
without fling, and offer an equivalent keyboard action if the card changes order.

## Current evidence

Current drag supports axis/constraints/elasticity, projected momentum, snap points/origin, outputs
and whileDrag. It writes transform directly and preempts the latest registry player. Pointercancel
uses pointerup release logic; touchAction is written during pointerdown; authored touchAction/userSelect
are cleared on end. No public drag-state signal, no external drag consumer in 014 and no physical
phone evidence. Existing tests cover basic mechanics; touch scrolling is Chromium CDP with limited
WebKit release assertions. [AUDIT](../AUDIT.md), [SDD §14](../SDD.md).

## Scope

One primary pointer lease, lost-capture/cancel/destruction distinction, predeclared touch-action,
exact style restoration, coordinate-root constraints, release/snap/momentum/reduced-motion semantics,
layout/exit/state integration, consumer drag state if needed. Reorder only as a bounded experiment
on matured layout and application-owned keys/array. Review target/trigger consumer distinctions.

## Non-goals

Generic multi-touch/pinch/swipe/input framework, application drag-drop policy, automatic array store,
reorder for parity, or physics/inertia options without a use case.

## Architecture implications

Drag owns translation while active; it must coordinate projection and whileDrag with one writer.
Cancellation releases capture/RAF and does not project momentum. Distinguish pointer input, release
settling and final app state without replacing Angular signals. Constraints must name coordinate space.

## Workstreams

1. Adversarial pointer/cancel/multiple-input/lost-capture fixtures and style restoration.
2. Layout/state/presence lease integration and constraints under scrolling/resizing.
3. Actual iOS/Android/pen-where-available validation plus accessible equivalent actions.
4. Decide bounded drag graduation and optional state/reorder; compare target/trigger use in consumers.

## Likely code areas

move-drag.directive and types/spec, ownership/transform internals, layout/presence integration,
interaction e2e/real app fixtures, docs, MCP. Reorder would get a separate directive spec only after demand.

## Test strategy

Touch panning before capture, outside pointerup, pointercancel/lost capture, second pointer, pen hover,
axis/constraints/elastic snap, resized/scrolled container, repeated drag baseline, destroy/revive and
state override mid-drag. Dynamic reduced motion/app disabled stops decoration while preserving direct
manipulation. Three-engine automation supplemented by recorded physical-device sessions and keyboard tests.

## Docs strategy

Explain touch-action/scroll tradeoffs, pointer lifecycle, constraints, outputs/state, momentum versus
inertia and keyboard alternatives. Show app-owned reorder logic and explicit unsupported multi-touch.

## Migration impact

Experimental drag/types can change with distinct notes; cancel behavior and touch policy require manual
review even when template compiles. Preserve same-origin snap recipes; bridge output details if practical.
Do not remove target/trigger merely because an imperative alternative exists.

## Performance considerations

Measure pointermove-to-paint, per-frame writes and constraint reads; batch only with latency evidence.
Stop work at rest/teardown; stress drag with layout and reactive values on low-end hardware.

## Accessibility

Functional pointer following remains under reduced motion; release snap/clamp is immediate, inertia
and decorative spring are disabled. Reorder must have keyboard/move-button equivalence, focus retention
and announcements; native click/link/scroll semantics remain usable.

## Risks

Touch cancellation timing, multiple pointer overwrite, hidden gesture RAF, transformed constraints,
keyboard omission and untested phone behavior. Retain experimental status when any blocking risk remains.

## Acceptance criteria

- [ ] Pointercancel/lost-capture/destruction end once, without unintended momentum or stale writes.
- [ ] Touch-action set before gesture, chosen panning works, authored styles restore exactly.
- [ ] Layout/state/presence/drag composition and constraints pass defined geometry contract.
- [ ] Actual iOS and Android tests plus keyboard equivalents are recorded.
- [ ] Reduced motion and app disabled semantics are consistent for release and whileDrag.
- [ ] Any drag state/reorder addition has a real workflow, performance evidence and separate API decision.
- [ ] Every drag type plus target/trigger initial disposition has evidence-backed review.

## Evidence required

Interactive consumer flow on phones, three-engine event/visual traces, pointer latency and cancel
resource counts, keyboard/manual accessibility report. Desktop emulation is supporting evidence only.

## Maintainer decisions

Touch-action defaults/axis policy, output cancellation detail, public drag state, bounded momentum
semantics and whether reorder adds value. Graduate drag only on evidence; no generic gesture framework.
