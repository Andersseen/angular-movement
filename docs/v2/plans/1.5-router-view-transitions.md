# 1.5 — Angular Router & View Transitions

**Status: future plan; no implementation started.** Depends on 1.4 task settlement/scope and 1.3
packed SSR fixtures. Uses Angular Router and native View Transitions; it does not build a router.

## Objective

Reliable navigation motion that respects Angular lifecycle, failure and browser fallback.

## User story

As a developer with guarded/nested routes, I can animate navigation and shared snapshots while rapid
navigation, redirect or unsupported browser still yields the correct final URL/view/focus.

## Current evidence

[1.2](../../ai/specs/014-consumer-dx-imperative-motion.md) animates pseudo-elements through MoveAnimator;
spring/per-property timing/inline commits are intentionally unsupported. The theme-reveal e2e is
Chromium, not a Router test; site uses provideFileRouter without a Movement adapter. Angular already
creates transitions around activation/deactivation and exposes a creation callback.
[Official Router guide](https://angular.dev/guide/animations/route-animations).

## Scope

Recipe suite using withViewTransitions, app-owned route data and shared snapshot names, safe ready/
finish handling, scoped pseudo playback, reduced motion and normal-navigation fallback. Add a small
experimental adapter only if two applications duplicate substantial glue; evaluate Angular 21/22
hooks and Analog integration separately. Define one transition for nested outlets.

## Non-goals

Second router, guard/resolver reimplementation, generic page manager, waiting for decorative presence
before activating routes, shared live layout promotion, or cross-document navigation abstraction.

## Architecture implications

Angular owns navigation/DOM commit; browser owns snapshots; Movement owns optional players. Keep
navigation generation and pseudo-selector identity separate from host and moveLayoutId. Cancel old
visual tasks on supersession without reverting committed app state. Native ready rejection/skip is
normal terminal behavior; no unhandled Promise and no hanging group.

## Workstreams

1. Native-first route/shared-element recipes with explicit browser support/fallback.
2. Navigation fixture with redirect/guard cancel/error/back-forward/query-only/nested-outlet cases.
3. Compare recipe duplication in two consumer apps; choose minimal adapter only on evidence.
4. SSR/hydration/reduced-motion and scroll/focus restoration matrix.

## Likely code areas

MoveAnimator pseudo path/base players, new optional adapter only if justified, consumer Router fixture,
`e2e/`, site recipes and global transition CSS, MCP guidance; package peer/entry changes require separate review.

## Test strategy

100 rapid navigations, failed guards/resolvers, redirects, nested outlets, superseding snapshot,
duplicate names, missing target, native ready rejection, normal/forced-unsupported paths, reduced
motion, direct SSR load/hydration/first client navigation. Browser capability checks must not hide
fallback failures. Test target host animation survives snapshot cancellation and vice versa.

## Docs strategy

State what Angular already solves, global pseudo CSS scoping, uniqueness rules, limited pseudo timing,
normal fallback, and progressive enhancement. Explain snapshots versus retained presence views and
shared layout identity. Recheck current native API docs during implementation.

## Migration impact

Recipes work with today's imperative API; optional adapter remains experimental. No required Router
peer for core consumers. Migrating legacy route triggers is manual/partial until lifecycle equivalents
are proved; route intent must not be inferred from arbitrary animation triggers.

## Performance considerations

Measure snapshot/setup latency separately from route data/load latency; avoid unnecessary full-document
captures and expensive snapshot names. No continuous Router subscription per animated element.

## Accessibility

Skip both native transition and custom animation under reduced motion while committing navigation.
Preserve focus, announcements, scroll restoration and link semantics. First hydration creates no motion snapshot.

## Risks

Upstream Router preview changes, browser pseudo targeting differences, snapshot duplication, double
transitions, and effects delaying navigation. Keep adapter tiny/version-tested and navigation independent.

## Acceptance criteria

- [ ] Navigation matrix passes for supported Angular majors and three engines with explicit fallback.
- [ ] Cancel/redirect/error/supersession never leaves stale players or unhandled promises.
- [ ] Shared-name/nested-outlet policy documented and validated in two distinct app flows.
- [ ] Packed SSR/hydration/no-JS and first-navigation focus/scroll behavior pass.
- [ ] Reduced motion commits route with no decorative transition.
- [ ] Adapter/package decision justified by actual duplicated code and bundle/peer evidence.

## Evidence required

Real navigation app plus SSR consumer; traces of final URL/view/focus and target ownership, native
feature status/browser versions, snapshot timings and compatibility artifacts.

## Maintainer decisions

Recipes only versus opt-in adapter; route-data convention; shared-name scope; optional Router entry/peer
only if isolation is useful. Do not promise provider names such as provideMovementRouter before approval.
