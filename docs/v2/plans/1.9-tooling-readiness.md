# 1.9 — DX, Tooling & 2.0 Readiness

**Status: future plan; no implementation started.** Depends on completed evidence/decisions from
1.3–1.8. Public preview of converged contracts, not the start of another subsystem.

## Objective

Freeze architecture and prove migration, diagnostics and all retained subsystems on candidate artifacts.

## User story

As a maintainer planning an upgrade, I can inspect ownership conflicts, dry-run exact future changes,
and see independently reviewable consumer/browser/SSR evidence before adopting a major.

## Current evidence

There is no inspector or complete v2 export-disposition ledger today. Current MCP supplies snapshot
examples/guidance; API/docs/package checks are useful but narrow. Only Chromium runs comprehensive e2e;
Firefox/WebKit are subsets. Layout/drag external validation and packed SSR/hydration are absent from
historical certification. [AUDIT](../AUDIT.md), [VALIDATION](../VALIDATION.md).

## Scope

Finalize all exports/members and experimental family decisions; rehearse confirmed migrations;
complete Angular/browser/environment/input/stress/real-consumer matrix. Evaluate dev-only inspector
using already-built ownership/result events. Record production tree-shaking and package boundary decisions.
Bug fixes/polish welcome; new architectural subsystems require deferral, not rushed 2.0 entry.

## Non-goals

Major new motion capability, inspector extension for novelty, mandatory production event log, introducing
a ownership mixer just for tooling, default removal of deprecated stable aliases, or fake passing skips.

## Architecture implications

No blocking ownership/cancellation/geometry/Router/scheduling decision may remain. Inspector reports
actual owner/channel/result/config without owning motion itself; bounded events and no retained detached
DOM. Architecture freeze permits only fixes that preserve agreed semantics and rerun affected evidence.

## Workstreams

1. Per-export/member ledger from 73 baseline declarations plus additions; migration cost/benefit review.
2. Dev diagnostics/playground prototype; ship inspector only if actual consumers find it useful.
3. Candidate tarball full matrix, physical touch and long-session reports; investigate skips/failures.
4. Dry-run/apply rehearsals in distinct apps; prepare major/no-major decision and support policy.

## Likely code areas

API snapshot/CI/consumer harness, migration tooling, dev-warn/opt-in diagnostic hooks, MCP snapshot,
optional development inspector, docs/migration/release checklist. No core rewrite or speculative package split.

## Test strategy

Every [readiness row](../VALIDATION.md) has artifacts and reviewer. Supported-major min/latest checks,
three-engine targeted contracts, physical devices, packed SSR/hydration, all-subsystem preference changes,
1,000 mount cycles/30-minute memory, rapid navigation and five-way ownership tests. Preview migration
is deterministic/idempotent and compiled/executed; production bundles contain no inspector listener/history.

## Docs strategy

Publish versioned preview contracts, public disposition ledger, explicit limitations, migration diffs,
unsupported/known manual steps and real measured reports. Preserve historical 1.x recipes and APIs.
MCP answers for preview must not imply candidate APIs are stable in earlier versions.

## Migration impact

Preview only confirmed changes; mechanical rename/import rules separate from manual ownership/lifetime
review. At least one minor notice/bridge where practical for experiments. Stable aliases have no removal
commitment; remaining breaks require concrete user benefit and comparison with additive alternatives.

## Performance considerations

Zero production inspector cost when absent, bounded development history, final narrow/core bundles,
setup/frame/heap regressions compared with baselines; no hidden tooling dependency in the runtime.

## Accessibility

Physical touch, keyboard/assistive manual reports plus all reduced-motion paths, focus during
navigation/exit/reorder, no-JS content. A diagnostics UI must itself be keyboard accessible if shipped.

## Risks

New tool scope delays evidence, false green matrices from skips, migration fatigue, insufficient
consumer availability and unresolved behavior hidden as polish. Publish blocked gates, defer major.

## Acceptance criteria

- [ ] Every export/member has reviewed stable/deprecated/promote/redesign/remove/internal disposition.
- [ ] No blocking architecture decision remains; all retained subsystem semantics existed in 1.x.
- [ ] Required matrix and four-consumer cohort pass on pinned candidate artifacts.
- [ ] Migration rehearsal/dry-run/apply/idempotence and manual-step effort recorded.
- [ ] Inspector build-or-reject decision documented; unimported production cost zero.
- [ ] Each proposed stable break has benefit/cost and failed additive-alternative justification.
- [ ] Maintainer records 2.0-ready or remain-1.x decision; missing evidence is explicit.

## Evidence required

Consumer-app revisions, browser/device/server traces, export ledger, bundle/heap reports, migration
review and maintainer approval of final scope. Demo tests or historical 1.2 results cannot certify this candidate.

## Maintainer decisions

Final dispositions, optional tool/package delivery, compatibility support window and major necessity.
If no valuable breaking change remains, continue 1.x with the proven system; 2.0 is not owed.
