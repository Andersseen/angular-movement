# 2.0 — Angular Motion System (conditional)

**Status: future conditional plan; no implementation started.** Requires every 1.9 gate and a justified
breaking-change benefit. Do not cut a major solely because the runway reached 1.9.

## Objective

Freeze a coherent long-term contract from capabilities proved in 1.x, with predictable upgrade cost.

## User story

As a production Angular maintainer, I can upgrade a mature motion system using reviewed migration
tooling/docs and rely on stable layout/gesture/ownership semantics already tested before the major.

## Current evidence

There is no proven necessity for a breaking 2.0 today. Most useful additions, richer settlement and
experimental revisions can ship in 1.x. [AUDIT](../AUDIT.md) identifies ownership/restoration as the
strongest boundary hypothesis; permanent aliases/package splits have no demonstrated removal benefit.
[SDD §24](../SDD.md) compares current API, alternatives, cost and why additive paths come first.

## Scope

Apply only 1.9-decided unavoidable stable changes, retire specifically approved deprecated/experimental
bridges, promote proved layout/gesture/other APIs, align lifecycle/ownership defaults if justified,
publish migration and compatibility contract. Package restructuring only if earlier opt-in evidence
shows a concrete peer/bundle boundary. All retained major capabilities already shipped during 1.x.

## Non-goals

First sequence/router/layout/reorder/value/devtool implementation, artificial alias cleanup,
new general gesture/router/editor system, last-minute public API invention, or automatic promotion
of every experiment. If no break remains, this milestone is not executed as a major.

## Architecture implications

Remove a legacy path only when its cost/benefit case and migration are settled. Freeze bounded support
contracts, not universal composition. Do not expose internal engine/coordinator/parent tokens simply
because architecture has matured. Stable controls still use resolving finished unless a separately
proved incompatible contract explicitly earns the change (current recommendation is retain).

## Workstreams

1. Confirm candidate evidence/artifact freshness and final break/no-break decision.
2. Implement only approved convergence/removals, retaining source-compatible APIs where useful.
3. Rerun exact migration from 1.9 to final tarball in cohort and supported matrices.
4. Publish final docs/support policy and release through separate authorized release workflow.

## Likely code areas

Only files named by final approved implementation spec: possible ownership defaults, experimental
bridges, barrel/API snapshot, package entries and migration tool/docs. Actual version bump/tag/publish
is a future release task; none is authorized or performed by this plan.

## Test strategy

Full gate from [VALIDATION](../VALIDATION.md), compatibility/removal negative tests, upgraded consumer
compile/runtime/SSR/hydration/touch/layout/navigation, no stale lifecycle resources, final migration
idempotence and narrow-import/production-tool cost. Fixes after readiness rerun affected candidate evidence.

## Docs strategy

Stable system overview and compatibility boundaries, complete before/after migration, known manual
cases, evidence references and 1.x archived docs. Explain why each break benefits applications; do not
market feature count as major value.

## Migration impact

Source-compatible promotions need no rewrite. Stable breaking behavior/default/import changes require
previewed tool/manual route and consumer effort report. Keep permanent aliases unless an explicit
reviewed benefit outweighs removal cost; no “deprecated therefore deleted” rule.

## Performance considerations

Compare final code to 1.9 preview and 1.2/narrow baselines, confirm deleting bridges improves actual
cost where claimed. Same runtime/frame/memory budgets apply; convergence cannot introduce hidden work.

## Accessibility

Final matrices include reduced-motion changes, no-JS/SSR readable content, keyboard equivalents,
physical touch and focus/scroll stability. Accessibility semantics form the stable compatibility contract.

## Risks

Rushed launch, untested removal, feature growth at major boundary and migrations that compile but
change visual/function behavior. No release while gate failures or blocking design questions remain.

## Acceptance criteria

- [ ] All retained major subsystems were shipped and validated before 2.0.
- [ ] Every break has approved additive-alternative analysis, benefit and tested migration cost.
- [ ] Final export/member/experimental ledger matches implementation and docs.
- [ ] Candidate tarball full matrix and upgraded real consumers pass with reviewed artifacts.
- [ ] Migration tool/docs work from 1.9; unsupported cases remain visible/manual.
- [ ] Production bundle/performance/lifecycle/accessibility contracts meet budgets.
- [ ] Maintainer authorizes separate release, or records that continuing 1.x is preferable.

## Evidence required

Final candidate hash, release gate record, cohort upgrades, physical-device proof, public API diff,
migration costs and meaningful-break justification. No completion status inferred from roadmap sequence.

## Maintainer decisions

Is a major necessary at all? Which unavoidable breaks passed evidence gates? Which experiments remain
experimental or leave with a migration? What is the maintained 1.x support policy? No unresolved ownership
question may be deferred into a supposedly stable release.
