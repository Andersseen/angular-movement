# 1.8 — Reactive Motion & Performance

**Status: future plan; no implementation started.** Depends on representative 1.4–1.7 workloads and
baselines collected from 1.3. This is an internal-quality milestone, not a flashy feature expansion.

## Objective

Prove reactive motion and lifecycle costs in long-lived, low-end and hidden-tab applications.

## User story

As a dashboard developer, I can use derived signal motion for hours and repeatedly mount views
without a growing heap, unnecessary idle frames or jump on returning to a background tab.

## Current evidence

moveValue is signal, moveTransform is computed with numeric/same-unit interpolation, and moveSpringValue
owns one RAF loop through injector effect cleanup. [013](../../ai/specs/013-post-1.0-hardening.md) counted
linear callback growth and no leaked mocked frames at 1/10/50/100, supporting unchanged architecture;
this is not p95 CPU/GC/device evidence. Precomputed and live spring paths differ. Smooth scroll remains
a singleton with idle RAF and separately scheduled momentum. [SDD §§15/20](../SDD.md).

## Scope

Browser/physical-device profiling at 1/10/50/100 and realistic several hundred, derived graphs,
setup/keyframe generation, teardown/subscriptions, garbage collection, hidden-tab/resume, invalid inputs,
transform bindings, dynamic reduced motion and whole-runtime stress. Decide smooth-scroll retention/
redesign/deprecation from actual need and native accessibility. Velocity/stronger derivation only if use cases earn them.

## Non-goals

Shared scheduler by intuition, custom observable/value classes, arbitrary CSS-string interpolation,
new physics engine, performance claims based on fake timers, or compulsory package split.

## Architecture implications

Keep pure computed derivations scheduler-free and injector cleanup independent. If measured shared
scheduling improves performance, prove isolated cancel/error/owner semantics and frame ordering.
Stop live work at rest; reset elapsed sample time on resume. Do not convert finite WAAPI playback into
per-frame signals. Retained transform binding must participate in ownership or use separate nodes.

## Workstreams

1. Build pinned browser/low-end workload benchmarks with framework/application controls.
2. Long-session/mount/destroy/hidden-tab and invalid-physics tests; inspect retaining paths.
3. Compare existing RAF versus a prototype scheduler only if budgets fail.
4. Decide velocity/derivation requests and smooth-scroll/native-scroll tradeoffs.

## Likely code areas

values/move-values, spring-player/constants, scroll/parallax/smooth-scroll, layout/gesture coordinator,
new benchmark harness, consumer workflows, CI report storage. Changes to stable value shape are out of scope.

## Test strategy

Deterministic lifecycle tests plus real tracing: 1/10/50/100 springs, multiple derived computed outputs,
retarget/destroy, two independent scopes, invalid/nonfinite inputs, source change while hidden, 60-second
background pause, 1,000 mount cycles and 30-minute session. Measure hardware/versions, five-run median/p95,
RAF idle counts, JS/layout/GC and retained detached DOM. Native keyboard scroll must not be fought.

## Docs strategy

Publish measured supported workloads/budgets, independent-loop decision, best practices for shared
sources/pure derivation, matching-unit constraints, hidden-tab behavior and smooth-scroll limitations.
Do not imply several hundred values are smoothly supported on all devices.

## Migration impact

Prefer internal compatible fixes. Experimental smooth-scroll can revise or deprecate with native
replacement recipes. Public velocity helper would start experimental with units/lifetime documented;
no migration from Angular signal return types.

## Performance considerations

Use [VALIDATION](../VALIDATION.md) budgets as provisional gates, ratified with recorded hardware.
Profile narrow-import bundle/core setup too. Scheduler benefit must exceed its allocation/coordination
cost under representative workloads, not just reduce callback count.

## Accessibility

Live springs emit target on reduced-motion changes; scroll interception relinquishes to native behavior.
Direct manipulation remains functional. Include focus scrolling and input responsiveness alongside frame speed.

## Risks

Noise interpreted as a win, scheduler coupling independent owners, hidden-tab velocity spikes, caches
retaining elements and smooth-scroll accessibility regression. Keep reproducible baseline/raw reports.

## Acceptance criteria

- [ ] 1/10/50/100 performance reports and realistic high-count characterization exist.
- [ ] Pure derivation adds zero RAF; rest/destroy leaves no active owned callback or detached DOM.
- [ ] Hidden-tab/resume, dynamic preference and invalid-input behavior are finite and documented.
- [ ] Memory/long-session/frame budgets met or supported scope explicitly narrowed with evidence.
- [ ] Scheduler kept/replaced based on fair measured comparison and independent-lifecycle tests.
- [ ] Smooth-scroll family has retention/redesign/deprecation proposal and native migration recipe.
- [ ] New derivation helper, if any, justified by concrete consumer use rather than parity.

## Evidence required

Long-lived dashboard and low-end interactive app traces, raw repeated benchmark samples, heap retaining
paths, tarball/narrow bundle measurements and manual keyboard/scroll report. Mocked RAF counts alone fail the gate.

## Maintainer decisions

Reference hardware/budgets, hidden-tab policy, shared scheduler threshold, velocity/derivation demand,
smooth-scroll future and any optional boundary. Architecture expansion stops after this milestone.
