# 1.4 — Motion Orchestration

**Status: future plan; no implementation started.** Depends on 1.3 adoption evidence and packed
runtime baseline. Lay ownership/cancellation groundwork here; final transform math belongs to 1.6.

## Objective

Give multistep Angular workflows one understandable lifetime, including cancellation and cleanup.

## User story

As a dashboard developer, I can cancel a reveal/save/exit chain when state changes or its component
is destroyed, without a resolved old animation launching the next step.

## Current evidence

MoveAnimator supports animate/set/clear but is a root service with no component teardown scope;
finished resolves for both cancellation and completion. [014](../../ai/specs/014-consumer-dx-imperative-motion.md)
deferred sequence because no audited flow required group controls. Variants/stagger provide delays,
not actual completion barriers. The registry retains only the latest player, so a broader group API
must not amplify hidden conflicts. [SDD §§8–10/17](../SDD.md).

## Scope

First collect two actual group use cases. Design experimental finite sequence/parallel/stagger task
trees, explicit owner scope, structured terminal result, nested propagation, interruption/error and
SSR/reduced-motion skip semantics. Prototype all-player/channel diagnostics and keep stable path
compatible. Evaluate trigger-handle duplication with imperative consumer migrations.

## Non-goals

General scrub/labels/editor timeline, arbitrary callback reversal, new custom signal classes, changed
finished rejection behavior, changed stable variants when delays or all-transform mixer promise.
If sequential await plus explicit cancellation scope solves use cases, avoid an unnecessary DSL.

## Architecture implications

AnimationControls remains a leaf handle. Experimental task controls need no currentTime/pause unless
finite precompiled timelines demonstrate need. Separate visual result from Promise<void>, invalidate
generation before settling, own delayed children, and cancel every descendant on destruction.
Track target/channel membership without globally cancelling independent properties.

## Workstreams

1. Specify terminal outcomes and owner/generation lifecycle; test null/server/disabled behavior.
2. Prototype smallest group shape versus scoped async recipes in real workflows.
3. Add nested/error/delay cancellation and channel-conflict diagnostics/equivalence fixtures.
4. Compare moveTrigger imperative handle with MoveAnimator + scope; document experiment, not removal.

## Likely code areas

`engines/animation-controls.ts`, base/composite players, MoveAnimator, active-player-registry,
animate-with-options, variants/trigger internals, consumer/e2e workflow fixtures and MCP examples.
Public additions need separate spec approval and API snapshot review.

## Test strategy

Start order and parallel barriers, heterogeneous/spring durations, rapid A→B→C replacement, abort during
stagger delay, external cancel, one child failure, destroy mid-await, detached target, Infinity rejection,
SSR and reduced-motion ordering. Preserve old mock controls/independent layering and finished behavior.
No later effect executes after cancellation; group resources reach zero on all terminal paths.

## Docs strategy

Explain when direct await is sufficient, what group cancellation means, why group controls differ
from leaf controls, and explicit business callback outcome checks. Add one real workflow, not a long
abstract sequence gallery. Keep stable variant delay estimates documented.

## Migration impact

Additive experimental task/scope API; no required change for stable users. Any trigger experiment gets
Changed (experimental), before/after recipe and bridge where practical. Do not make a new required
AnimationControls member that breaks application mocks.

## Performance considerations

Measure task setup/allocated handles, many delayed targets and teardown; no resting global RAF or
MutationObserver. SSR/disabled paths cannot leak timer work. Preserve WAAPI leaf playback.

## Accessibility

Reduced motion skips visual delays while preserving ordered app intent. Cancellation must not leave
focus in an inaccessible intermediate UI; functional state callbacks remain application-owned.

## Risks

Overdesigned tree API, cancellation interpreted as success, undocumented ownership changes, guessed
spring barriers. Result visibility and compatibility fixtures are prerequisites to shipping groups.

## Acceptance criteria

- [ ] Two consumer flows justify scope/groups, or documented smaller alternative meets objective.
- [ ] Nested sequence/parallel/stagger terminal/error/skip/cancel semantics pass tests.
- [ ] Owner destruction cancels active and pending work; stale callbacks/commits are zero.
- [ ] Stable controls/variants/independent property behavior remains compatible.
- [ ] Channel tracking prototype explains concurrent conflicts, including pseudo-target isolation.
- [ ] Experimental API feedback and complete teardown/performance artifacts reviewed.

## Evidence required

Dashboard async workflow and interactive staged flow on packed candidate; failure/interruption traces,
compatibility tests and measured setup costs. Demo sequence alone does not justify stabilization.

## Maintainer decisions

Group DSL versus scope recipes; result shape; persistence on cancel; explicit owner API; trigger handle
future. Ownership default stays opt-in until layout/touch prove it and any stable break is separately approved.
